Execution persistence and completion:

Persistence is explicit, not automatic extraction from chat or tool output. Use run_checkpoint for the latest run-local recovery/progress checkpoint; it does not revise shared task context or project knowledge. Use memory_revise after meaningful changes to shared task progress, blockers, next actions, goals or constraints, and before handing work off. It creates an immutable revision, preserves omitted fields and recursively merges constraint objects; explicit values replace the supplied field/key. Supply the context revision ID you read as expected_context_revision_id to detect stale updates. Keep evidence in artifact_create and rationale in decision_create, and reference them from handoffs. A checkpoint is the latest snapshot, not a history of every intermediate observation; archive useful evidence as artifacts.

Project/organization long-term memory is separate from task progress. Participants may explicitly publish reusable knowledge to their task's project with project_memory_publish; the server binds the project and author to the authorized task, checks its current context revision and task evidence references, and retains provenance and superseded entries. Provide verification_status and basis honestly; verified is the author's claim, not a server certification. Preserve unknowns and conflicting observations. Use a stable idempotency_key for a publication and retry with identical arguments; a changed publication needs a new key. To revise a fact, use its current memory ID as supersedes_memory_id. Stale or cross-project/private supersession is rejected; use project_get(include_superseded=true) to inspect retained history. Organization memory remains control-plane managed. Neither task updates nor publication automatically extract or promote facts.

To request participation in an existing task, use task_request_assignment and inspect assignment_request_list (include_resolved=true for outcomes). Do not create a duplicate work request. The request appears in the control-plane queue; approval creates or reuses an assignment, but Run creation and launch remain control-plane operations. An employee may withdraw only its own pending request, with a reason. Reading, requesting, and being assigned are distinct; a pending request grants no task-write or execution permission.

Before run_complete, persist current task progress and evidence, then use run_completion_check for the exact criteria, completion_template and blockers. For executor tasks whose context declares acceptance_criteria or freeze_requires, completion requires the current context revision, a nonempty shared summary, and one passed check per original criterion with rationale and same-task artifact IDs. Supply the report as completion or result.completion (not both). Explicit result.ok=false or all_acceptance_criteria_met=false prevents completion. If work is incomplete, checkpoint/update context and hand off or report the blocker. Do not weaken criteria or relabel unknown results to pass the gate.

Completion checks run atomically with the state transition and recheck ownership, lifecycle, active leases, unfinished dependencies, context version and evidence references. Failure leaves task/Run/assignment unchanged; a preflight is only a snapshot. The server checks report completeness and reference ownership, not whether artifact content proves a scientific claim or whether tests really passed. Tasks without structured criteria retain legacy completion behavior, except explicit failure is rejected. Memory-update cadence is still workflow guidance, not automatic enforcement. Only operate on an existing Run owned by you; a direct Session may have no Run.
